# 既存プロジェクトへの Hora Kit 適用

Hora Kit は通常「そこから始めるテンプレート」として出会います。こちらはもう一方の場合です — renchan のバックエンドと furo のフロントエンドが既にあり、動くコードを持っていて、その周りにキットを被せたい。

**既存リポジトリは何ひとつ奪われません。** 履歴もブランチも設定もコードもそのままです。Hora Kit はそれらの**外側**に立ち、仕様書と計画と記録を持つリポジトリです。

---

## 適用して何が手に入るのか

「残りをキットが作ってくれる」ではありません。それは後の話です。**最初に手に入るのは、この製品が今何をできるのかという事実です。**

「既に作られている」と宣言された機能は、作り方を述べた17の関所を飛ばしますが、**検収には必ず入ります。** つまり適用後の最初の掃引は、既存製品全体を、その製品自身が掲げるユースケースに対して受入レビューすることになります — どこに到達でき、何が揃っていて、失敗したときに本当のことを言うか。

**指摘が出ることを見込んでください。そしてそれが、適用した価値そのものです。**

その後は、新しい機能が18関所を1つずつ通っていきます。

---

## 始める前に

| | |
|---|---|
| **リポジトリが renchan / furo 系であること** | 関所は `backend-renchan-*` と `frontend-*` のスキルに委譲し、それらはその規約を述べています。別スタックのリポジトリでも順序と関所は効きますが、委譲される手順はすべて「それではないもの」を説明することになります |
| **バックエンドは1つ、DB システムも1つ** | 方針は `1 DB システム = 1 リポジトリ`。0個または2個以上は止まって尋ねます |
| **Node と npm**（キット自身の `npm install` 用） | |
| **Claude Code** | |

**フロントエンドは任意です。** スマホアプリ向け API だけ、という案件もあります。

---

## 目指す形

```
myproject-app/                  ← キット。specs/ .hora/ .claude/ を持つ。アプリコードは持たない
  legacy-api/                   ← 既存のバックエンド。手つかず
  admin-console/                ← 既存のフロントエンド。手つかず
```

**入れ子は git の要求ではなく Claude Code の要求です。** セッションは作業ディレクトリの外に書けないので、触る必要のあるリポジトリは中に入っている必要があります。

**ディレクトリ名は変えなくて構いません。** `Directory` 列はそのために在ります。

---

## 手順1 — 既存リポジトリの周りにキットを作る

新規プロジェクトと同じ手順で `<myproject>-app` をこのテンプレートから作り（[README.ja](../README.ja.md) の「始め方」）、既存リポジトリを中に移します。

```sh
mv legacy-api admin-console myproject-app/
cd myproject-app
npm install
```

**移動するか、新しく clone してください。シンボリックリンクは駄目です。** リンクされたリポジトリは、リポジトリ単位のコマンドがすべて依存している作業ディレクトリ規則を壊し、しかも壊れ方が間接的です — コマンドは走り、間違った設定を読み、もっともらしい結果を返します。

**既存の `.git` には何もしません。** [`boilerplates.md`](../.claude/skills/hora-setup/references/boilerplates.md) にある `rm -rf .git && git init` は**boilerplate を新規 clone した場合**の手順で、他人のコミット数百件が製品リポジトリの `main` に着地しないためのものです。**既に存在したリポジトリはこれを丸ごと飛ばします** — キットはその上に**被せる**のであって、**上書きする**のではありません。

---

## 手順2 — 「既にあるもの」として仕様書を書く

空の仕様書をコピーして埋めます。

```sh
cp specs/skeleton/spec.md specs/1.0.0/spec.md
```

各節の説明は [`spec-format.md`](../.claude/skills/hora/references/spec-format.md) にあります。適用時にはそのうち3つがいつも以上に重要です。

### 2.1 リポジトリ構成表に `Directory` 列

```markdown
## 2. Repository layout

| Repository | Origin | Role | Directory |
|---|---|---|---|
| `myproject-backend` | renchan | the API and jobs (holds the DB) | `legacy-api` |
| `myproject-frontend-admin` | furo | the admin screens | `admin-console` |

### 2.1 Servers

| Server | protocol | consumer |
|---|---|---|
| `admin-graphql` | GraphQL | `frontend-admin` |
| `worker` | — | an API server in the same repository (no contract needed) |
```

| | |
|---|---|
| **`Directory` を書くと** | `/hora-setup` はそこを見て、**clone しません。** 書かれていること自体が「既に存在する」の宣言です。無ければ、その名前の上に何かを作る代わりに止まって尋ねます |
| **`Repository` 列も依然として重要** | `target` の値は**この列**から来ます。`Directory` からではありません。`target` は `.hora/tasks/` に残る恒久的な分類で、ディレクトリは誰かのディスク上の場所です。後でフォルダを改名しても `.hora/` の中身は動きません |
| **既定名に従う行では列を省く** | 両方が混在するのはごく普通です |

**サーバー表は省略できません。** contract はここから導出され、どのフロントエンドがどの contract を読むかもここで分かります。

### 2.2 既に存在する機能すべてに `built:`

適用を可能にしているのがこの注釈です。

```markdown
## Attendance
<!-- id: attendance -->
<!-- target: backend, frontend-admin -->
<!-- built: frontend -->
```

| 値 | 意味 | n/a になる関所 |
|---|---|---|
| *(省略)* | まだ何も無い | 無し — 新規機能の通常ケース |
| `spec` | 仕様はある。コードは無い | 1–2 |
| `backend` | バックエンドゲートぶんは既にある | 1–9 |
| `frontend` | フロントエンドゲートぶんも既にある | 1–17 |

**関所18 はどの値でも覆われません。** 何を書いても `[ ]` のまま残ります。それが設計のすべてです：**適用は動くものを作り直さないが、本当に動くのかは確かめる。**

**自分で書いてください。キットは推論しません。** 半端な画面と完成した画面はファイル一覧からは区別できず、ここで推測を外すと、それを捕まえたはずの関所を黙って飛ばすことになります。宣言の無い機能は、コードがどれだけ完成して見えても関所1から計画されます。

**`built:` を付けた機能にも、想定ユースケースと受入基準は書いてください。** 関所18 はそれに対して検証するので、どちらも無い `built:` 機能は「何に対して検収するのか」が存在しません。

### 2.3 既存資産

```markdown
## 4. Existing assets

Current implementation: legacy-api, admin-console (adopted in place)
Treatment: keep it — Hora Kit is being adopted onto these repositories, not used to rewrite them
```

**この節は本来別のことを意味します** — 「この古いコードを新リポジトリに移植する」か「振る舞いだけ合わせて書き直す」か。適用の文脈では正直な答えはたいていそのどちらでもなく、**ここでそう明記しておくことが、ある関所が「書き直す」と判断するのを止めます。**

## 手順3 — `/hora` を走らせる

```
/hora
```

リポジトリが宣言されているのに全部は揃っていないと判定し、まず `/hora-setup` を走らせます。適用済みの行に対しては、こうなります。

| 手順 | 適用済み行での挙動 |
|---|---|
| 最新タグの取得、clone、`.git` の破棄 | **丸ごと飛ばす** |
| **除外リストへのディレクトリ登録** | **`.gitignore` と `eslint.config.js` の両方に追記される**（後述） |
| `package.json` の name/description | **プレースホルダのままの場合だけ**埋める |
| `.env.development` | **キーが空のままの箇所だけ**埋める |
| `docker.sh` / `docker-compose.development.yml` | **絶対に上書きしない。** 既にあれば読み、仕様書の手動検証表との差分を報告する |
| `npm install` | 実行する |
| `bank-id` の backend へのコピー | **まだ無い場合だけ** |
| 実物ツリーの読み取り | 実行し、読んだ時点の boilerplate タグとともに `.hora/tree/` に控える |

**そのどれもが独立した冪等チェックであって、全部か無しかのスキップではありません。** 人が既に埋めたものは上書きされません。

### 除外リストが見た目より重要な理由

`.gitignore` とルートの `eslint.config.js` は、実装リポジトリを**名前で**除外しています（`*-backend*/`, `*-frontend*/`）。`legacy-api/` はどちらにも当たらず、**どちらの失敗も無言です。**

| | 起きること | 気づく経路 |
|---|---|---|
| `.gitignore` | バックエンド全体が追跡され、**キットのリポジトリに**コミットされる | `git status` を読むまで無い。その時点で既にコミット済み |
| `eslint.config.js` | ルートの lint が、自分のものではない設定のリポジトリを走査する | そのリポジトリが同意していない規則に対する大量の違反 |

`/hora-setup` は宣言された `Directory` ごとに1行ずつ両ファイルに追記し、追記したことを報告します。**それが起きたか確認してください** — 適用手順の中で、抜けたときの損害が大きく、しかも静かなのはここだけです。

---

## 手順4 — 何かを作る前に計画を読む

次に `/hora-plan` が走ります。版を確定し、仕様書が決めていないことを尋ね、機能一覧を書きます。

**`built:` が正しいかを確認するのはこの瞬間です。** 計画には機能ごとに「いくつの関所が既に n/a か」が出ます。完成しているつもりだったのに何も宣言しなかった機能は関所1から計画され、`built: frontend` と宣言した機能は関所18 だけが開いた状態で並びます。

**どちらに間違えても、今なら安く、後だと高くつきます。**

| 間違え方 | どうなるか |
|---|---|
| `built:` と宣言したが実は作られていない | 検収が落とし、印が解除され、本当に作られる — **安全な方向** |
| 宣言しなかったが実は作られている | 動くコードに対して17の関所が走る。壊れはしないが、時間が無駄になる |

---

## 手順5 — 最初の検収掃引

開いている関所が18 だけの機能は、コードを書かず、ブランチも切りません。`/hora-build` はそのまま `/hora-accept` に入ります。

```
1. 環境の確認        ローカル E2E 群が実際に動くこと
2. ユニットスイート   既存のテストを、そのまま実行
3. シナリオ一覧      API が公開しているものから導出
4. 受入レビュー本体   到達可能性、CRUD の充足、アフォーダンス、
                     失敗と待ちを正直に伝えているか
5. UX の指摘         深刻度付き。プロジェクト context に対して
```

**手順1 で最初の実行が止まる可能性が高く、それは正常です。** 関所17 はローカルの E2E 環境を作るために在り、既存プロジェクトはたいてい**何かしら**（compose ファイル、シードスクリプト）を持っていますが、前提条件 — アプリの背後で全サービスが動き、各ロールでサインインでき、レビュー可能なデータがある — をまだ満たしていません。それを直してから再実行してください。

**飛ばさないでください。フロントエンド単体でレビューしないでください。** そのやり方で走らせたレビューは、**得ていない合格を報告します。**

### 指摘の意味

各指摘は「どの機能の、どの関所に戻すか」を書きます。適用済み機能の *built before Hora Kit was adopted* と印された区間に着地した場合、**その印は解除されます** — 直さなければならないコードは、結局のところ単に受け継いだものではなかったからです。影響する最も手前の関所から、本当に作ります。

これが、既存製品がキットの水準まで引き上げられていく仕組みです。**一度に1つの不足だけ、しかも不足が実際に示された箇所だけ。**

## 気をつけること

### boilerplate のタグが既存コードより新しい

`/hora-setup` は実物ツリーを読み、読んだ内容をタグとともに控えます。既存リポジトリは、現在の boilerplate が前提とする規約より前の世代かもしれません。**実物はあらゆる想定に勝ちます** — 読み取り手順が在る理由がそれです — が、委譲されるスキルは**現在の**規約を述べるので、同じリポジトリの中で新しいコードが古いコードと違って見えることがあります。それは想定内で、パッケージが既に離れた規約に対して新しいコードを書くよりは望ましい状態です。

### 履歴のあるリポジトリに `release/<version>` を切る

キットはどのリポジトリでも `release/<version>` の上で作業します。適用済み行では、そのブランチは fetch 後の `origin/main` から切られます（新規 `git init` からではありません）。空の `Release <version>` 開始マーカーは同じように付きます。

**`main` に直接コミットしないでください。** キットのリポジトリでは `main-guard.yml` が main への PR を `release/*` `hotfix/*` `dev` `env` に制限していますが、既存リポジトリにはその防壁が無いかもしれず、うっかり破りやすくなっています。

### 既存の eslint 設定と、こちらの設定

各リポジトリは自分の設定で、自分の中から lint します。キットのルート設定は実装リポジトリを**決して** lint しません — 除外リストはそのために在ります。既存設定が `@openreachtech/eslint-config` と食い違う場合、そのリポジトリの中では既存設定が勝ち、関所はそれに合わせて動きます。

### 既存のテスト

`/hora-accept` の手順2 で、そのまま実行されます。**通すために弱められることはありません** — スキップも削除も緩和も待ち回避もしません。既存テストが落ちたなら、それは迂回すべき障害ではなく**指摘**です。

### CI

`.github/workflows/` のワークフローは `light` ラベルのセルフホストランナーで動きます。用意できない場合、**`runs-on` を自分で書き換えないでください** — `specs/<version>/spec.md` にその旨を記載してください。

## 短くまとめると

```
1. このテンプレートから <myproject>-app を作り、既存リポジトリを中に移す
2. specs/1.0.0/spec.md を書く：
     - リポジトリ構成表に、既存リポジトリごとの Directory 列
     - 既に存在する機能すべてに built: spec | backend | frontend
     - 想定ユースケースと受入基準は、作られているか否かに関わらず全機能に
     - 既存資産: そのまま活かす
3. /hora
     - setup は clone を飛ばし、両方の除外リストにディレクトリを登録し、
       プレースホルダのままの箇所だけ埋める
     - plan が未決事項を尋ねる
4. 計画を確認する：built: は全部正しいか？
5. 最初の検収掃引が、製品が実際に何をできるのかを教える
6. そこから先は、新しい機能が18関所を1つずつ通る
```
